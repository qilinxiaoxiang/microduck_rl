A — Turn a call and spoken request into one caller-bound fetch job

Where/why: the start of the demo, and the identity needed at its end. Existing name response and speech components do not yet prove one shared audio path or persistent caller binding. This task advances P1/P4/P6. Difficulty 3/5; project novelty 2/5. Week-one software increment is ready; live caller/gaze acceptance needs B/E and a robot window.

Build: an audio-to-event adapter that emits call, orange-ball request and cancel for the correct caller. Reuse existing wake/ASR components; keep interpretation narrow first. Do not write joints or a timed action sequence. Walking calls request stop through E; seated calls preserve seated posture.

Start with supplied material

From this package: cd starter/interaction then python3 run.py. No installation, credentials or hardware. The supplied fabricated transcripts produce 21 regression checks and expose two unsupported utterances. python3 run.py --events call_then_fetch prints the actual event stream consumed by the coordinator. Read ADAPTER.md, cases.json and reference/ for existing source and its dependencies.

Suggested operations

  1. Run the baseline and inspect the typo/paraphrase misses. Add a small separately held-out phrase set, including the actual Chinese request “去把那个橙色的球捡回来”, unrelated conversation, cancellation and a second speaker. Implement bounded normalization/intent handling and keep ambiguous requests unresolved.
  2. Implement one audio producer that fans time-stamped chunks to wake detection and transcription. Start from supplied source references. Use local WAV input first; then your laptop microphone. The same bytes must reach both consumers; neither opens a second microphone. No teammate needs Shawn's private CLI subscription.
  3. Add the transcript/event adapter and replay the same recordings. For real caller binding, consume B's person candidates and associate the call with a visible person; retain a re-matchable cue through the trip. Until that evidence exists, emit unknown identity instead of choosing anyone nearby.
  4. Feed the events into E. Test a call while walking, a call while seated, a second person, and cancel during approach/pick. E owns when movement may stop/resume; A supplies intent.

Deliver and accept

Week 1: code, one command, the local shared-audio replay, labelled transcripts and the resulting events. Freeze negative utterances before tuning; all expected positive requests and cancellations in the stated set must match their caller, and no negative may start a fetch. Report misses/false starts with denominators, not a single “accuracy.” Demonstrate both consumers saw identical chunk IDs/times. Retain the original baseline results for comparison.

Week 2, with B/E: show original caller → look → fetch event → original caller retained when another person speaks or the caller moves. Do not count fabricated identities as passing this gate. A/B jointly own identity; A/E jointly own call/cancel transitions. If identity is uncertain, the expected output is no fetch and a clarification request.

Handoff: source revision, recording/label provenance, command and JSON events. The starter's 10-second request window is a changeable development choice; record the chosen value. This task is complete only at its claimed software or live-input level, clearly distinguished.

B — Keep the selected ball or original caller in view and approach it

Where/why: outward trip and return use the same visual following behavior. Existing orange detection/gaze code does not prove “ball” identity, continuous tracking near the mouth, or return to the right person. This task advances P0/P1/P6. Difficulty 4/5; project novelty 3/5. Image/protocol work starts now; movement calibration waits for F0/C/D.

Build: target selection, temporal tracking and gaze/velocity requests for ball and person modes. Output intentions and observation age; C handles balanced joint motion. E decides which target/phase is active.

Start with supplied material

From starter/vision, follow README.md to create the pinned environment, then run .venv/bin/python run.py --out out. It includes the actual orange detector, a composite positive image, no-orange negative and orange non-ball challenge. Inspect the annotated outputs and tracks.jsonl: the rectangle is a preserved false positive, not a solved benchmark. Eight explicit track cases exercise identity/loss handling; person identities are fixtures, not recognized people.

Suggested operations

  1. Keep the baseline output. Add ball/non-ball and self-orange-part negatives before tuning; record lighting/viewpoint split. Begin with size/shape/temporal consistency around the existing detector; add a compact semantic detector only if this baseline fails the frozen distractors. Never special-case a supplied filename or pixel position.
  2. Maintain one selected target across frames. Use the supplied current gaze/controller source reference to turn image-center error into head requests. Add a genuine person-observation adapter and a reidentification cue shared with A; a tracker ID that resets after looking away is insufficient.
  3. Keep capture time and freshness through occlusion. Use short history to search/reacquire; stale/unknown identity requests a stop, not continued forward motion. Show selected target, age, gaze error and request overlaid on video.
  4. Add approach speed/turn requests constrained by C's supported range. Use a configurable D entry profile and E wait zone. First exercise them with supplied protocol fixtures; after F0 calibrate them with actual camera/body readback and continuous B/C → D entries.

Deliver and accept

Week 1: code plus a replay command that produces overlays and track/request JSON from the frozen clips. Compare to the original detector; report ball recall, distractor false selections, identity switches, stale-command duration and latency with counts. Every wrong/uncertain/stale target must stop approach in the contract tests. Improving one published rectangle does not establish generalization.

Week 2, conditional: jointly demonstrate B/C reaches D's published entry range from varied starts, then B/C/E returns to the original caller after that person moves beside a distractor. Preserve complete failures, not selected clips. Before trials, freeze the test starts and measured wait/pick ranges; success means arriving inside those ranges without manual target/pose correction. The first gate is range compatibility, not an invented universal centimeter threshold.

Handoff: target adapter, timestamps/identity semantics, selected-target recording, movement requests, supported camera/head range. B/C own gaze-versus-balance; B/D own entry; A/B/E own original-person return. If D's region is not yet known, software work proceeds with a fixture profile and physical entry remains pending.

C — Walk, turn and stop while actually looking down

Where/why: looking at a ball changes whole-body balance. A smooth policy that barely moves or refuses to lower its head does not solve the demo. Later the same controller must carry the ball. This advances P5/P6. Difficulty 5/5; project novelty 3/5. CPU baseline/diagnostic work starts now; new-body training waits for F0.

Build: improve the existing walker to follow head/neck and velocity requests together. Start with unloaded motion, then extend to D's real loaded exit. Preserve a named supported range for B/E.

Start with supplied material

Use starter/motion/README.md to install its pinned CPU environment. Run python replay.py locomotion --out out/gait.json with that environment. The package contains real walk61 and t2b exports, bounded historical sensor/action traces, source snapshots and hashes. It reproduces the head-down jitter comparison. Raw 61-value observations were not logged: reconstructed-input inference is explicitly approximate, not exact controller parity. Historical models are not accepted for the new backpack.

Suggested operations

  1. Reproduce the default-head versus lowered-neck trace diagnostic. Inspect action jumps alongside head error, speed/distance and tilt. Check compensation/filtering/observation semantics; the package documents the opt-in compensation trap.
  2. Inspect the supplied finetune/environment source. Prepare a two-condition evaluation using identical velocity commands, head commands and initial states. After F0, run it unchanged on the matched model. If it cannot reproduce the relevant failure, first fix model/actuator/timing agreement; do not hide mismatch by changing reward weights.
  3. Compare one change: retain velocity/head tracking while adjusting the original-policy leg reference strength. Keep head joints outside an anchor that would force the old head pose. Reject changes that reduce jitter by not walking or not looking down. A short observation/action history is a later comparison if measured timing uncertainty is the unresolved limitation; its benefit alone does not prove the physical cause.
  4. Evaluate B's recorded requests, then D's supported loaded exit. Export through the pinned input/action adapter and replay the same tests. Do not infer compatibility from equal vector length.

Deliver and accept

Week 1: baseline readback, evaluation code/config and one precisely specified comparison; a CPU diagnostic is already possible. Supply action-jump rate, head error, travel/velocity tracking, tilt and falls together. Preserve failed traces. No new-body training claim before F0.

After F0: freeze a physically reachable head/velocity range and trial starts before tuning. Candidate must improve the preselected failure metric while retaining required head/velocity tracking and stable stop across the range. Record real-condition and stress results separately. Compare at least two training seeds if compute permits; one seed is exploratory, not established robustness. Only a matched exported version passing protected robot trials advances to live B/D integration.

Handoff: model/source/config hashes, units/joint mapping, supported head/velocity/payload range, previous-action/history initialization, all seeds and failures. D does not wait for this new model to begin isolated development: both start from the shared historical baseline after F0. Loaded walking is the next increment after D supplies a validated exit and payload.

D — Pick the ball and hand over in a stable loaded state

Where/why: a closed beak is not delivery. Historical pickup has failed from visual loss, empty bites and a fall after switching to standing. This advances P0/P5/P6. Difficulty 5/5; project novelty 4/5. Replay/source work starts now; a changed physical policy waits for F0.

Build: a continuous visual pickup through stable loaded rise, with explicit failure/readback and compatible entry/exit regions. Keep visual history through near-mouth occlusion. The final result must be safe for C to carry, not merely a terminal reward at bite time.

Start with supplied material

In the CPU environment described by starter/motion/README.md, run python replay.py pickup --out out/handoff.json. Actual pixel-pick and stand exports, bounded robot traces and source snapshots are supplied. Inspect the neck mismatch and observed fall timing around the pick→stand switch. This locates a concrete transition problem; it does not prove that the mismatch alone caused the fall or that smoothing alone fixes it.

Suggested operations

  1. Reproduce the failed transition and compare sensor state, outgoing action and incoming controller target. Read reference/T2-PIXEL.md and the copied environment/worker. The actor gets image features/age/visibility; simulator-only object truth must stay out of the deployed actor.
  2. Extend the task through a stable loaded exit and a short carry/stop segment. Start after F0 from measured stable baseline entry states, so D need not wait for a new C model. Publish the tested entry/exit region. B/C then generate actual entry samples; replace ideal starts with those samples.
  3. Keep source timing/contact settings fixed. Audit rewards against standing still, empty closing, floor contact, early termination and the intended pick. Require lifted-and-held success and stable exit; score each component. Compare the current task with the extended terminal objective before adding history or extra reward terms.
  4. Implement named pick/stand/walk adapters preserving actual pose, velocity, previous action and visual history. Do not blend two raw 61-input/14-action policies. Add empty-bite, visual-loss and drop outcomes, and a supported cancel exit consumed by E.

Deliver and accept

Week 1: reproduced handoff trace, executable continuous-transition evaluation, and the exact single comparison. State what outcome would change the next action: failure before lifting changes perception/contact work; failure after lift changes exit/control work.

After F0: freeze starts drawn from B/C exits. In one uninterrupted trial, the ball leaves the floor, remains held through rise, then C carries and stops. Record entry compatibility, lift, retained grip, tilt/falls, empty bites and drops separately; retain every failure. Validate payload sensing on real positive/negative examples—jaw current alone can mean floor contact or a jam. Simulator contact truth may judge training but cannot certify the robot.

Handoff: actor/config, entry/exit profile, payload/exit readback, supported abort and failure cases. B/D and D/C jointly accept transitions without resetting body or ball. E owns return and human-take logic; D supplies the grip/payload evidence it needs. Full physical pickup within two weeks is an aim, not a guaranteed output.

E — Complete the fetch, return and human handover in one runtime

Where/why: independently good modules do not make a fetch robot. This task explicitly owns sequencing, return, waiting, authority and recovery so those steps do not disappear into “integration later.” It advances P0/P4/P6. Difficulty 4/5; project novelty 3/5. Motor-free composition starts now; live readback depends on the producing tasks/F0.

Build: connect A/B/C/D to the existing single motor executor; retain original caller and payload through the entire job. A complete result is return to that caller and wait for the person to take the ball. A safe stop/help is a valid failure outcome, not a successful delivery.

Start with supplied material

From starter/, run python3 rehearse.py. Standard library only. It imports the actual A parser, reads a saved B detector result and composes 22 scenarios. Read out/rehearsal.json, coordinator.py and CONTRACT.md. Reproduce with fresh B output via python3 rehearse.py --tracks vision/out/tracks.jsonl. All physical acknowledgements are labelled fixtures; this is not a simulated or real fetch success.

Suggested operations

  1. Trace the complete scenario and its failure branches. Add a small runtime adapter that maps named intents to the supplied existing executor source in runtime-reference/. In observation-only mode, log intended commands and actual body/sensor readback without sending motor commands.
  2. Replace fixture acknowledgements one at a time: C provides settled; B/D provide entry; D provides lift/hold/supported exit; B/C provide wait-zone arrival. E implements verified human-take detection with D's payload evidence and labelled take/drop clips. Unknown must stay unknown.
  3. Bind each command/result to the active task epoch and one motion owner. Cancel requests a supported exit; manual/emergency revokes all old work. Calls during walking wait for stop; calls during picking do not interrupt the body controller. Protect loaded grip from quacks/expressions.
  4. Integrate original-caller search, approach, wait and take. On target loss, stop/reacquire; on empty bite, return to a validated search state; on unsupported exit or drop, stop/help. Add autonomous retries only from states the adjacent controller can accept.

Deliver and accept

Week 1: observation-only adapter, complete transition log and positive/negative readback examples. All 22 supplied cases must retain their expected outcomes; add actual producer-output replays as they arrive. Test expired camera data, wrong person, cancel during bite and old queued commands after manual takeover. A timer or a Boolean written by the coordinator cannot stand in for physical success.

Week 2, conditional: one continuous A→B/C→D→B/C→wait/take trial, plus wrong-person, loss/drop and cancellation branches. Bind video and logs to one source/model version. No reset or manual target correction between segments. Count interventions and failure stages. Freeze the physical trial set before testing; this plan does not certify a success rate in advance.

Handoff: adapter, event log, authority/readback tests and a restart procedure that cannot resume an old job. E shares each transition check with its producer. If a sensor cannot distinguish take from drop, mark the handover gate incomplete and request help; do not relabel object disappearance as delivery.
